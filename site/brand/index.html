01 / Identity

A lowercase d, drawn in one line.

The open loop looks like a mark made on a canvas. It connects directly to drawing, while the rising stem gives it a recognizable silhouette. Keep that geometry intact.

Room to breathe

The SVG's square includes the intended clear space. Keep its full viewBox and add at least one stroke width outside it when placing it beside other content.

Use the mark at 24 px or larger in the interface. The favicon is the special 16–32 px case; use the prepared export.

16 / 24 / 32 px

Preserve proportions and round terminals. Avoid rotation, extra strokes, shadows, or a gradient on the wordmark. Use the supplied dark version rather than recoloring the light logo by eye.

Quiet feedback

Use color feedback on controls. Avoid decorative entrance animations and animated logos. Respect reduced motion.

Aim for at least 4.5:1 for normal text and 3:1 for meaningful control boundaries. Provide a visible keyboard focus ring, useful labels and a 44 px target for primary touch controls. Contrast is measured for the samples here; this is not a claim that the whole application has been audited.

07 / Integration

Use one source. Generate the rest.

The marketing site already consumes this kit. Application adoption is a separate step: its operational tokens, screens and permissions have been preserved in this delivery.

  1. Update the source, not an export

    Edit brand roles in apps/frontend/src/globals.css. The selected mark is design/brand/logo.svg; the outlined lettering is design/brand/wordmark.svg. The guide and marketing CSS use the generated token export. 

    node site/build-brand.mjs
node site/export-brand-png.mjs
bash site/build.sh

    SVG and CSS generation needs Node. PNG regeneration uses the repository's Playwright dependency and Chromium: run npm ci and npx playwright install chromium first. Normal Pages builds use the checked-in PNG exports and verify that their sources match.

  2. Apply the roles in the application

    Import the generated font CSS once, copy the supplied fonts with their licenses, and replace old logo assets with the corresponding light/dark exports. Adapt the existing shared UI classes to the brand roles rather than hardcoding hex values in screens. 

    /* A primary action, in either theme */
.primary-action {
  background: var(--color-brand-action);
  color: var(--color-brand-on-action);
  border-radius: var(--radius-brand-control);
}
.primary-action:hover {
  background: var(--color-brand-action-hover);
}
.primary-action:focus-visible {
  outline: 3px solid var(--color-brand-action);
  outline-offset: 3px;
}

    Apply the generated .theme-dark mapping on the app's theme root, or port that mapping into its existing :root.dark rule. Check sign-in, dashboard, editor shell and sharing in both themes. Changing a background alone can leave old white button text unreadable.

  3. Set up product link previews

    Keep og:image and twitter:image absolute, pointing to the social PNG on the final host. The Pages home includes them. If you reuse the site under another host or base path, update its canonical URL and social metadata together. 

    <meta property="og:image"
  content="https://rodacato.github.io/drawhaus/brand/assets/social-card.png" />

  4. Preview and publish with GitHub Pages

    The existing Pages workflow serves site/_site. The product home is /drawhaus/, the guide is /drawhaus/brand/, and the application remains independently hosted. 

    bash site/build.sh
node site/check.mjs
python3 -m http.server 8117 --directory site/_site

    That quick server previews the output at http://localhost:8117/. Before publication, also serve it under the /drawhaus/ project base path and check direct loads. Merge through the repository's normal PR flow; Pages deploys from master. A local build does not publish the site.
